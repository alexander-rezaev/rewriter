# Если словарь терминов станет слишком большим

Словарь нужен, чтобы редкие названия, индексы и аббревиатуры **не перефразировались**. Его не стоит превращать в полный глоссарий языка.

Сейчас в коде:

- не больше **500** терминов;
- термин не длиннее **120** знаков;
- **весь** список подмешивается в промпт каждый запрос;
- перед рерайтом каждое слово из словаря ищется в тексте регуляркой.

На T-lite контекст **4096** токенов. Длинный словарь съедает место у самого текста, модель начинает путаться и копировать «Словарь терминов» в ответ (это уже чинилось отдельно, но раздутый список снова ухудшит качество).

---

## Когда словарь «слишком большой»

Ориентиры, а не жёсткие пороги:

| Симптом | Что происходит |
| --- | --- |
| Рерайт медленный на коротком абзаце | сотни регулярок по каждому термину |
| Модель игнорирует стиль или повторяет куски промпта | список терминов не влезает в контекст вместе с текстом |
| Обычные слова перестают перефразироваться | в словарь попали частые слова («отдел», «работа») |
| Подсвечивается не то / ломаются числа | короткий термин вроде `1` или `KPI` совпадает внутри других слов |

Практичный потолок для этой связки: **несколько десятков** живых терминов, лучше **до ~100**. 500 — аварийный лимит, не цель.

---

## Что делать сразу, без правок кода

1. **Оставьте только то, что модель реально ломает.** Имена подразделений, изделия, внутренние шифры, «1С», «KPI», если его переписывают. Не заносите каждое существительное из документа.
2. **Не кладите в словарь целые предложения.** Одна строка «1 отдел 1 управления службы безопасности Яндекс» занимает слот и почти абзац в промпте. Лучше короткое устойчивое имя: «служба безопасности Яндекс».
3. **Не добавляйте слова из общего языка.** «безопасность», «сотрудники», «отдел» словарь защищать не должен.
4. **Чистите мёртвые записи.** Раз в какое-то время откройте `/terms` и удалите то, чего уже нет в работе.
5. **Короче формулировка.** До 3–6 слов. Длинные казённые названия режьте до узнаваемого ядра.
6. **Один смысл — одна запись.** Не дублируйте «KPI», «kpi» и «Kpi»: защита и так нечувствительна к пробелам по краям, а лишние варианты раздувают список.

Этого обычно хватает, чтобы упереться не в лимит 500, а в здравый смысл.

---

## Если терминов реально сотни

Тогда упираетесь уже в архитектуру, не в таблицу на экране.

1. **В промпт уже уходят только термины из текущего текста.** Полный JSON на диске может быть большим, в модель попадают только совпадения. Это уже сделано.
2. **Искать вхождения не перебором regex.** Для сотен и тысяч строк нужен автомат (Aho–Corasick) или индекс. Сейчас каждое слово всё ещё ищется отдельной регуляркой.
3. **Поднять `num_ctx`, если тексты длинные.** У T-lite в Modelfile стоит 4096. Больше контекст — больше RAM и медленнее CPU. Имеет смысл только вместе с пунктом 1, а не вместо него.
4. **Разнести словари по контурам.** Отдельный `terms.json` для бухгалтерии и для службы безопасности, менять файлом на сервере, а не сваливать всё в один список.
5. **Не поднимать лимит 500 «на всякий случай».** В промпт больше не льётся весь список, но каждый термин всё ещё проверяется регуляркой на каждый запрос.

Пункт 2 — следующая доработка, если словарь дойдёт до сотен строк. До этого держите список коротким.

## На офлайн-сервере

Словарь живёт в `data/terms.json` рядом с `docker-compose.yml` (том `./data:/app/data`). Большой файл можно править с ноутбука и копировать на сервер. Пересобирать Docker-образ для этого не нужно, достаточно положить JSON и не трогать контейнер (или `docker compose restart`).
